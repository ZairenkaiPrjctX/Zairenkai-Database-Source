## Dump layout (verified on both hosts)

```
<group>/<namespace>/<project>          namespace is usually a brand, project usually a codename
  branch <build description>           e.g. sys_mssi_64_64only_ww_armv82-user-16-BP2A...-release-keys
    all_files.txt                      one path per line
    vendor/ odm/ product/ system_ext/  extracted partitions
    system/system/...                  system-as-root image: real /system is system/system/
    system/<root files>                root filesystem of that image (not a partition)
    aosp-device-tree/, README.md, ...  generated by the dumper, not firmware
```

Namespaces and project names are **hints only**. Example of why: the Nothing Phone (3a)
dump lives at `nothing/Galaga`, but its `vendor/build.prop` first defines the MediaTek
reference device (`alps`/`mgvi`) and only later Nothing/`Galaga`; Android uses the last
definition, and so does AFID's parser. The project README of the same dump disagreed with
its own build fingerprint (Android 16 vs 14). Identity therefore comes only from the fetched
`build.prop` (evidence type `dump_build_prop`), never from names.

## Relationship between the two hosts

The two hosts are **independent dumps, not mirrors**: 301 relative project paths exist on
both, 24 also share the default branch name, and none of a 24-branch sample shared a commit
SHA. They use different dumpers (gitlab.com dumps carry `README.md`, `all_files.sha1` and
`proprietary-files.*`; tadiphone dumps carry `kallsyms.txt`, `boot.elf`, `ikconfig`). For
the same build, `vendor/build.prop` and `system/system/build.prop` had identical Git blob
ids on both hosts (e.g. `asus/asus_x00td`, `nokia/hpe`).

Dedup rule, implemented in [MATRIX_PIPELINE.md](MATRIX_PIPELINE.md#reconcile): same brand,
codename and build (build id + incremental + region/channel) from build.prop gives the same
firmware key, so both hosts land in **one firmware record with two `source_refs`**. The
fetched vendor `build.prop` blob id is stored as each ref's `content_marker`. A second
source with a different build fingerprint, or a different hash for any common file, is a
conflict: it is quarantined in staging (`codename_status: conflict`) and nothing is
overwritten (`test_conflicting_dump_is_quarantined`).

## How AFID uses a dump source

1. `afid discover --provider <id> --write` lists projects and branches into
   `database/sources/<id>/<namespace>.json` (one `firmware` item per branch, revision =
   commit SHA; one file per namespace keeps every file far below the 5 MB repository limit:
   the 8772-item tadiphone snapshot is 306 files, the largest 958 KB).
   Projects whose repository API answers 404 (70 on tadiphone) are recorded as
   `repository_not_readable` markers, not errors.
   Projects whose `last_activity_at` did not change are not re-listed; projects with no
   branches are remembered as `index` markers. A listing with fewer than `min_projects`
   projects is a failed check, so a broken response never marks items removed.
2. `afid firmware analyze --provider <id> --item <item>` fetches build.prop files and the
   files a classification rule could match, pinned to the commit, within the fetch budget,
   then follows DT_NEEDED of fetched vendor binaries (see [COMPONENT_ANALYSIS.md](COMPONENT_ANALYSIS.md)).
3. Results go to a delta store and are merged by `afid catalog reconcile`.

AFID never clones these repositories, never downloads firmware archives from them, never
writes to them and never follows LFS pointers.

## Directly mirrored, licensed source files

The separate `source-files/lineageos_wiki/` directory holds the original `_data/devices/*.yml`
files from the LineageOS Wiki. Its footer declares CC BY-SA 3.0; each mirror includes attribution,
the immutable upstream commit, a source URL, Git blob id and SHA-256. These files are copied
unchanged for maintainers to inspect. They are reference metadata, not firmware, binaries or
verified device evidence. AFID's transformed candidates remain in `database/staging/`.

The weekly `Mirror LineageOS Wiki source files` workflow checks out only `_data/devices/`, bounds
the number and size of files, parses them with `yaml.safe_load`, and validates the manifest before
opening or updating a PR. Its proposal job can change only `source-files/lineageos_wiki/`; it
creates at most 50 files per GitHub commit so the initial snapshot is processed in manageable
chunks. A PR review is required before any source snapshot is added to the default branch.
